🤔 Deep into Container — How Kubernetes Works with Container Runtime

November 23, 2022 Kubernetes Container Runtime Docker DevOps

Continuing the previous post, we learned about the Container Runtime. In this post, we are going to learn about a rather exciting topic — how Kubernetes uses the Container Runtime to manage containers at scale.

If you've ever wondered what happens under the hood when you run kubectl run, you're in the right place. Let's dive deep into the relationship between Kubernetes and container runtimes.

🔔 How Kubernetes Works with Container Runtime

Kubernetes doesn't directly create containers. Instead, it delegates this work to a container runtime through a standardized interface called CRI (Container Runtime Interface). This abstraction allows Kubernetes to work with different container runtimes without being tightly coupled to any specific one.

flowchart TB subgraph K8s["Kubernetes"] API[API Server] SCHED[Scheduler] KUBELET[Kubelet] end subgraph CRI["Container Runtime Interface"] CRIAPI[CRI API] end subgraph Runtimes["Container Runtimes"] CONTAINERD[Containerd] CRIO[CRI-O] end subgraph LowLevel["Low-Level Runtime"] RUNC[runc] end API --> SCHED SCHED --> KUBELET KUBELET --> CRIAPI CRIAPI --> CONTAINERD CRIAPI --> CRIO CONTAINERD --> RUNC CRIO --> RUNC style KUBELET fill:#3b82f6,color:#fff style CRIAPI fill:#10b981,color:#fff style RUNC fill:#f59e0b,color:#000

Here's the flow when you create a Pod:

  1. You submit a Pod spec to the API Server
  2. The Scheduler assigns the Pod to a Node
  3. The Kubelet on that Node receives the Pod spec
  4. Kubelet calls the container runtime via CRI
  5. The runtime executes commands to create the container

📢 Docker

Docker was the first container runtime that Kubernetes used, but in version 1.24 it was removed and is no longer supported.

Kubernetes used to interact with Docker through a component called dockershim. The problem? It was too cumbersome. Docker is a complete container solution with many features that Kubernetes doesn't need, adding unnecessary overhead.

flowchart LR KUBELET[Kubelet] --> SHIM[dockershim
DEPRECATED] SHIM --> DOCKERD[dockerd] DOCKERD --> CONTAINERD[containerd] CONTAINERD --> RUNC[runc] style SHIM fill:#ef4444,color:#fff style KUBELET fill:#3b82f6,color:#fff
⚠️ Important: If you're upgrading Kubernetes to version 1.24 or later, you'll need to migrate away from Docker to another container runtime like containerd or CRI-O.

📢 Containerd

Containerd is a simpler and less cumbersome container runtime than Docker. It's actually what Docker uses under the hood!

From version 1.1, containerd has a built-in CRI plugin. The kubelet can interact directly with this plugin — no shim layer needed. This is much more efficient.

flowchart LR KUBELET[Kubelet] --> CRI[CRI Plugin] subgraph CONTAINERD["containerd"] CRI --> CORE[Core] end CORE --> RUNC[runc] style KUBELET fill:#3b82f6,color:#fff style CRI fill:#10b981,color:#fff style CORE fill:#10b981,color:#fff

As you can see, instead of going through multiple layers with Docker, containerd provides a direct path from Kubelet to the container runtime. This means:

  • Lower resource overhead
  • Faster container startup times
  • Simpler architecture
  • Better maintainability

📢 CRI-O

CRI-O is another popular container runtime designed specifically for Kubernetes. It was developed by Red Hat and is the default runtime in OpenShift.

CRI-O is purpose-built for Kubernetes — it implements the CRI specification and nothing more. This makes it lightweight and focused.

🎯 Conclusion

So we've learned how Kubernetes works with container runtimes. The key takeaways:

  • Kubernetes uses CRI to communicate with container runtimes
  • Docker support was removed in Kubernetes 1.24
  • Containerd and CRI-O are the recommended alternatives
  • Both provide direct CRI integration without extra layers

If you're running Kubernetes in production, make sure you're using a supported container runtime. Containerd is a great choice for most use cases, while CRI-O is excellent if you're in the Red Hat ecosystem.
