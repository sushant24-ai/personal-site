🎯Service Mesh on Kubernetes — Istio Introduction

November 22, 2022 Kubernetes Istio Service Mesh DevOps

🟢Deploying the microservices system on the server is always a big challenge, and when Kubernetes was released, it made it somewhat easier to deploy the microservices system on the server. But we will face the next challenge is how to communicate between services inside Kubernetes, because Kubernetes was not born as networking solution, so Istio was released. Istio was developed based on Service Mesh.

With Kubernetes we use Pods to deploy services, before learning about Service Mesh, we will see: How do the Pods inside Kubernetes communicate with each other? And what is it restricted?

📌 Internal Pod Communication

✔️Kubernetes uses CNI as an interface between network providers and Kubernetes pod networking. In a Worker Node so that Pods can communicate with each other, Kubernetes uses kube-proxy.

✔️kube-proxy is a network proxy that runs on each node in your cluster, implementing part of the Kubernetes Service concept. kube-proxy maintains network rules on nodes. These network rules allow network communication to your Pods from network sessions inside or outside of your cluster.

✔️When we create a Pod or Service, kube-proxy will update the Iptables rules so that the Pods can communicate with each other, for example:

sequenceDiagram participant PodA as Pod A participant IPT as Iptables participant SvcB as Service B participant PodB as Pod B PodA->>IPT: Request to Service B Note over IPT: Replace destination IP
with Pod B IP IPT->>PodB: Forward request PodB-->>PodA: Response

👉When we create a Service B, the Kubernetes API Server will notify the kube-proxy at the worker node to update the Iptables rules and add the rule for Service B. Then if there is a Pod that calls Service B, its request will go through Iptables first. Next Iptables will replace the destination IP in Packet X with the IP of Pod B and forward the request to Pod B.

Limitations of kube-proxy:

  • The request it sends to the Pods is random
  • Traffic cannot be divided by percentage
  • Canary releases or blue-green releases cannot be performed
  • Hard to monitor and debug

Modern microservices systems need communication between services can be security, auto-retry, observability, monitoring, etc… But to perform these functions we need to add them to your own code.

There is nothing wrong, but these processes are taking up resources of the main application and need to write more code and we don't want that. Thus, the Service Mesh was born.

🎯 Service Mesh

✔️A service mesh is a dedicated infrastructure layer that you can add to your applications for facilitating service-to-service communications between services or microservices. It allows you to transparently add capabilities like observability, traffic management, and security, without adding them to your own code.

Service Mesh has two components: the data plane and the control plane.

  • The control plane manages and configures the proxies to route traffic.
  • The data plane is the communication between services. The data plane is typically implemented as a sidecar deployed alongside application code.

When the Service Mesh runs on Kubernetes, the data plane is deployed as a sidecar container that should run along with the main container in the Pod. These sidecar containers handle the communication between the services in the Pod.

🔴Now instead of managing communication between the Pods through kube-proxy. The Pod communicates with the sidecar container, and the sidecar container handles the communication between the Pods.
🔴All features such as security, auto-retry, observability, and monitoring are left for the sidecar container to do, the application only needs to focus on business logic.
🔴The two most popular Service Mesh tools at the time of writing are Istio and Consul, and we are going to talk about Istio.

Istio

✔️Istio is an open-source service mesh that layers transparently onto existing distributed applications. Istio's powerful features provide a uniform and more efficient way to secure, connect, and monitor services.

✔️Istio also has two components: the data plane and the control plane. The control plane using Istiod container and the data plane will be deployed to Pod as a sidecar using an Envoy container.

Istiod provides service discovery, configuration, and certificate management. Istiod converts high-level routing rules that control traffic behavior into Envoy-specific configurations and propagates them to the sidecars at runtime.

Envoy proxies are deployed as sidecars to Pods, Envoy's many built-in features, for example:

  • Dynamic service discovery
  • Load balancing
  • TLS termination
  • HTTP/2 and gRPC proxies
  • Circuit breakers
  • Health checks
  • Staged rollouts with %-based traffic split
  • Fault injection
  • Rich metrics

If we install Istio on Kubernetes and then create a Pod, the Envoy container will automatically be injected into our Pods. So we don't need to manually declare the Envoy container when writing the manifest file for the Pod.

Currently, Istio has been accepted as a project of the Cloud Native Computing Foundation (CNCF) 😁.

🤗 Conclusion

We have learned why we should use Service Mesh in microservices and what is Istio. Service Mesh solves the networking challenges in Kubernetes by providing a dedicated infrastructure layer for service-to-service communication, allowing your applications to focus purely on business logic.
