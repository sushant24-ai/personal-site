How to Build a Custom Agent Harness

June 5, 2026 AI Agents LangChain Middleware Architecture

building useful agents is largely about customization: connecting your agent to the right context, data, and environment(s) for the task at hand.

at its core, an agent is a model calling tools in a loop until it completes a task and returns a result. watch the loop cycle below — this is the heartbeat of every agent:

📥 Context In
→
🧠 Model Call
→
🔧 Tool Call
→
📤 Result Out
repeats until the task is done

you can also define an agent as:

agent = model + harness

the harness is the scaffolding around the model that connects it to the real world. the model reasons; the harness grounds that reasoning in your systems, policies, and data.

🎯 Two assumptions for the rest of this post 1. An agent is only as good as the context provided to the model.
2. The job of a harness is to provide context to the model at every step.

so, to build a useful agent, you need a harness that's great at delivering the right context for the given task to the model — at the right time, in the right shape.

1 The Base Harness

create_agent is LangChain's primitive for building a harness. pass in a model, tools, and a system prompt, and you have a working agent: 

from langchain.agents import create_agent

agent = create_agent(
    model="anthropic:claude-sonnet-4-6",
    tools=tools,
    system_prompt="you are a helpful assistant..."
)

under the hood, this wires up the core loop:

sequenceDiagram participant U as User / Caller participant H as Harness participant M as Model participant T as Tools U->>H: task + initial context loop until task complete H->>M: messages + tool schemas M-->>H: tool call or final answer alt tool call H->>T: execute tool T-->>H: tool result H->>H: append result to history else final answer H-->>U: return result end end

but not all harnesses are built the same way. there are two broad approaches:

⚡ Pre-assembled harnesses

  • Deep Agents, Claude Agent SDK
  • Memory, context mgmt, sandboxing baked in
  • Production-ready out of the box
  • Great for most cases
  • Less room for fine-grained control

🔧 create_agent (minimal)

  • Implements only the core agent loop
  • Middleware as the customization primitive
  • Similar philosophy to Pi (coding agent)
  • You compose exactly what you need
  • More work upfront, tighter task fit
💡 When to go custom Many agents need finer-grained customization than pre-assembled harnesses support: custom prompting, business logic, guardrails, model routing, and domain-specific tool lifecycles. That's where create_agent + middleware shines.

2 Middleware — How You Customize the Harness

middleware hooks into the agent loop at each step: before and after model calls, before and after tool calls, at agent startup and teardown. each piece handles one concern and composes freely with any other:

middleware gives you four levers that often work together:

⚙️

Deterministic Logic

Business rules, policy enforcement, model swapping, prompt adjustment, message history compaction — anything that can't (or shouldn't) live in a prompt.

🔧

Tools

Full tool lifecycle: setup, teardown, registration. Keeps tool config close to the logic that governs it, not scattered across the agent definition.

📦

Custom State

Extend agent state with counters, flags, or values that persist across hooks and share data between middleware pieces.

📡

Stream Handlers

Intercept and transform the output stream — filter events, inject metadata, route token deltas to UI, tool calls to audit logs, latency to monitoring.

the beauty of middleware:

  • Customize at any point in the agent loop
  • Bundle related logic in composable, sharable units of code
  • Reuse across agents — new agents inherit battle-tested behavior without rebuilding it

example: a simple guardrail middleware

from langchain.agents.middleware import AgentMiddleware

class BudgetGuardrail(AgentMiddleware):
    """Stop the agent if token spend exceeds budget."""

    def __init__(self, max_tokens: int):
        self.max_tokens = max_tokens
        self.tokens_used = 0

    async def after_model(self, state, response):
        self.tokens_used += response.usage.total_tokens
        if self.tokens_used > self.max_tokens:
            raise RuntimeError(f"Budget exceeded: {self.tokens_used} tokens")
        return state

agent = create_agent(
    model="anthropic:claude-sonnet-4-6",
    tools=tools,
    middleware=[BudgetGuardrail(max_tokens=50_000)],
)

3 Harness Capabilities

the job of a harness is to get the model the right context at the right time for the given task. here's how common production needs map to middleware:

Capability What It Does Middleware Pattern
Context compaction Summarize or trim message history before the context window overflows before_model — rewrite history, inject summary
Memory & retrieval Pull relevant past conversations or facts into the current turn before_model — RAG injection, episodic recall
Guardrails Enforce policies, block unsafe actions, cap spend before_tool, after_model — deterministic checks
Human-in-the-loop Pause for approval on sensitive tool calls before_tool — interrupt, await confirmation
Model routing Swap to a cheaper or stronger model based on task complexity before_model — dynamic model selection
Tool lifecycle Initialize connections, tear down sandboxes, scope tools per run on_agent_start, on_agent_end
Observability Trace latency, token usage, tool outcomes Stream handlers + after_model / after_tool
Prompt injection defense Sanitize tool outputs before they re-enter the model context after_tool — filter / redact untrusted content

most production agents end up using several middleware pieces together, depending on the agent's needs: is it long-running? how complex are the tasks? how sensitive are the agent's actions?

4 Task-Harness Fit

task-harness fit is how well your harness matches the actual demands of the task: the context it needs, the failures it'll encounter, the policies it must enforce, the environment it operates in.

a harness for a customer service agent looks very different from one built for a long-running coding agent. same model, different scaffolding:

Customer Service

Short turns, high stakes

Needs: CRM tool access, response guardrails, escalation to human, conversation memory. Middleware focus: guardrails, HITL, retrieval from knowledge base.

Coding Agent

Long-running, tool-heavy

Needs: filesystem + shell tools, sandboxing, context compaction, streaming to UI. Middleware focus: tool lifecycle, compaction, stream handlers.

GTM / Sales Agent

Data-rich, policy-bound

Needs: CRM + email tools, spend caps, audit logging, model routing for drafts vs. sends. Middleware focus: observability, guardrails, model routing.

every agent LangChain builds — including their GTM agent, asynchronous coding agent, and no-code agent builder — is built on create_agent with a middleware stack tailored to that agent's mission.

Putting It Together

building a custom harness is a three-step exercise:

  1. Start with create_agent — model, tools, system prompt. You have a working loop.
  2. Identify context gaps — what does the model need at each step that the base harness doesn't provide?
  3. Add middleware — one piece per concern. Compose, don't monolith.

the best agents aren't just built with capable models.

they're built with harnesses that tightly fit the task.

the easiest way to build a custom harness is with create_agent.
