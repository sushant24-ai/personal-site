Kubernetes for ML Workloads: Lessons Learned

December 15, 2025 Kubernetes ML Ops

After spending the past year running machine learning workloads on Kubernetes in production, I've learned quite a bit about what works and what doesn't. Here are my key takeaways for anyone looking to run ML infrastructure on K8s.

🎯 The Challenge

Running ML workloads on Kubernetes is different from typical web services. You're dealing with:

  • GPU scheduling — GPUs are expensive and scarce
  • Long-running jobs — Training can take hours or days
  • Large data — Models and datasets are often many gigabytes
  • Bursty resource needs — Inference scales differently than training

📊 Lesson 1: GPU Scheduling is Hard

Out of the box, Kubernetes treats GPUs as a simple resource like CPU or memory. But GPUs are different:

  • They can't be shared between pods (usually)
  • Different GPU types have vastly different capabilities
  • GPU memory matters as much as count

What we did:

resources:
  limits:
    nvidia.com/gpu: 1
  requests:
    nvidia.com/gpu: 1
nodeSelector:
  gpu-type: a100
  gpu-memory: 80gb

We use node labels to ensure workloads land on the right GPU type. We also implemented time-slicing for inference workloads that don't need a full GPU.

💾 Lesson 2: Data Locality Matters

Pulling a 50GB model from object storage every time a pod starts is a recipe for slow cold starts and high egress costs.

Our approach:

  • Use persistent volumes with ReadWriteMany access mode for shared model storage
  • Cache models on node-local SSDs using init containers
  • Pre-pull images with model weights baked in for critical services

📈 Lesson 3: Autoscaling Needs Tuning

The default Horizontal Pod Autoscaler (HPA) uses CPU metrics, which is useless for GPU workloads. Inference services need custom metrics based on:

  • Request queue depth
  • GPU utilization
  • Request latency

We use KEDA (Kubernetes Event-Driven Autoscaling) with custom metrics from our inference servers:

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: inference-scaler
spec:
  scaleTargetRef:
    name: inference-deployment
  triggers:
    - type: prometheus
      metadata:
        query: avg(inference_queue_depth{service="model-a"})

💰 Lesson 4: Cost Optimization is Critical

GPU nodes are expensive. A single A100 node can cost $15,000+/month. We saved significant money by:

  • Using spot instances for training jobs (with checkpointing)
  • Right-sizing GPU types — not every workload needs an A100
  • Implementing scale-to-zero for dev/staging environments
  • Bin-packing multiple small models on shared GPUs

🔧 Lesson 5: Observability is Non-Negotiable

When a training job fails after 6 hours, you need to know why. We instrument everything:

  • GPU metrics — utilization, memory, temperature
  • Training metrics — loss, accuracy, throughput
  • Infrastructure metrics — node health, network I/O

We use DCGM Exporter for GPU metrics and push them to Prometheus. Grafana dashboards give us visibility into the entire ML infrastructure.

🎯 Key Takeaways

  1. Plan for GPU scarcity — implement proper scheduling and quotas
  2. Optimize data access — cold starts kill user experience
  3. Custom metrics for autoscaling — CPU metrics are useless for ML
  4. Control costs aggressively — GPU bills can spiral quickly
  5. Invest in observability — you can't optimize what you can't measure

Running ML on Kubernetes is challenging but rewarding. The flexibility to scale training jobs and inference services independently is powerful. Just be prepared for the learning curve.
